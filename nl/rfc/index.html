Wanneer is een RFC nodig?

Niet elke wijziging heeft een RFC nodig, alleen belangrijke. Gebruik de tabel hieronder om te beslissen.

Soort wijziging RFC nodig? Proces
Nieuwe pijler of verwijdering van een pijler Ja RFC → TSC-stemming → PR
Wijzigingen in het scoringmodel (PASS-niveaus, wegingen) Ja RFC → TSC-stemming → PR
Breaking change in het controlschema of de ID's Ja RFC → TSC-stemming → PR
Voorstel voor een nieuwe werkgroep Ja RFC → lazy consensus → charter gepubliceerd
Wijzigingen in governance of rollen Ja RFC → gekwalificeerde TSC-meerderheid
Nieuwe control (niet-breaking, aanvullend) Aanbevolen PR met link naar de discussie, lazy consensus
Formulering van documentatie, typfouten, vertalingen Nee Alleen PR
Website-inhoud, blogposts Nee Alleen PR

Statusverloop van een RFC.

Elke RFC volgt hetzelfde gedocumenteerde pad, van eerste concept tot afgeronde beslissing.

draft
De indiener schrijft het voorstel in GitHub Discussions
→
open
Minimaal 5 werkdagen open voor commentaar van de community
→
accepted
TSC-stemming of lazy consensus, openbaar gedocumenteerd
→
implemented
PR gemerged, changelogregel toegevoegd, RFC gesloten
Alternatieve uitkomsten: rejected (na review niet geaccepteerd), withdrawn (ingetrokken door de indiener). Beide worden met redenen gedocumenteerd.

Zo schrijf je een goede RFC.

Drie dingen die het verschil maken tussen een RFC die snel vooruitgaat en een die vastloopt.

Beschrijf het probleem, niet de oplossing

Begin met wat kapot is of ontbreekt, niet met wat je wilt bouwen. Reviewers moeten het eens zijn dat het probleem echt is voordat ze je oplossing kunnen beoordelen. Leg het ‘waarom’ uit vóór het ‘wat’.

Laat afwegingen en alternatieven zien

Een sterke RFC legt uit wat er nog meer is overwogen en waarom dat is afgewezen. Dat bespaart reviewrondes en geeft toekomstige maintainers context als de oorspronkelijke indiener er niet meer is.

Wees concreet over de impact

Wie wordt geraakt? Welke repositories, bestanden of openbare contracten veranderen? Hoe duidelijker de reikwijdte, hoe sneller de community bruikbare feedback kan geven en een maintainer kan beslissen.
