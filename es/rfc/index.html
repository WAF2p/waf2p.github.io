¿Qué requiere una RFC?

No todos los cambios necesitan una RFC, solo los importantes. Usa la tabla de abajo para decidir.

Tipo de cambio ¿Hace falta RFC? Proceso
Nuevo pilar o eliminación de un pilar Sí RFC → votación del TSC → PR
Cambios en el modelo de puntuación (niveles PASS, pesos) Sí RFC → votación del TSC → PR
Cambio incompatible en el esquema o los ID de los controles Sí RFC → votación del TSC → PR
Propuesta de un nuevo grupo de trabajo Sí RFC → lazy consensus → carta publicada
Cambios de gobernanza o de roles Sí RFC → mayoría cualificada del TSC
Nuevo control (compatible, aditivo) Recomendado PR con enlace a la discusión, lazy consensus
Redacción de la documentación, erratas, traducciones No Solo PR
Contenido del sitio web, entradas del blog No Solo PR

Flujo de estados de una RFC.

Cada RFC sigue el mismo camino documentado, desde el primer borrador hasta la decisión cerrada.

draft
La autoría redacta la propuesta en GitHub Discussions
→
open
Mínimo 5 días hábiles abierta a comentarios de la comunidad
→
accepted
Votación del TSC o lazy consensus, documentada públicamente
→
implemented
PR fusionado, entrada en el registro de cambios añadida, RFC cerrada
Resultados alternativos: rejected (no aceptada tras la revisión), withdrawn (retirada por la autoría). Ambos se documentan con sus motivos.

Cómo escribir una buena RFC.

Tres cosas que marcan la diferencia entre una RFC que avanza rápido y una que se estanca.

Plantea el problema, no la solución

Empieza por lo que falla o falta, no por lo que quieres construir. Los revisores deben coincidir en que el problema es real antes de poder valorar tu propuesta. Explica el «porqué» antes del «qué».

Muestra compromisos y alternativas

Una buena RFC explica qué otras opciones se consideraron y por qué se descartaron. Ahorra rondas de revisión y da contexto a futuros maintainers cuando la autoría original ya no esté.

Concreta el impacto

¿A quién afecta? ¿Qué repositorios, archivos o contratos públicos cambian? Cuanto más claro el alcance, antes podrá la comunidad dar feedback útil y un maintainer tomar una decisión.

Da forma a la próxima decisión.

Elige una RFC abierta, comparte tu punto de vista o abre una nueva. El framework se construye en público y cada voz cuenta.
