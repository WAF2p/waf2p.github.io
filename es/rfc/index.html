¿Qué califica como RFC?

No todos los cambios necesitan una RFC — sólo significativa. Utilice la tabla de abajo para decidir.

Tipo de cambio RFC necesita? Proceso
Nuevo pilar o eliminación de un pilar Sí. RFC &rar; TSC vote &rar; PR
Cambios en el modelo (pantallas PASS, pesos) Sí. RFC &rar; TSC vote &rar; PR
Cambio de ruptura para controlar esquema o ID Sí. RFC &rar; TSC vote &rar; PR
Nueva propuesta del Grupo de Trabajo Sí. RFC → lazy consensus → charter publicado
Cambios de gobernanza o función Sí. RFC &rar; Supermajoridad TSC
Nuevo control (no rompedor, aditivo) Recomendado PR con el enlace de discusión "middot; consenso perezoso
Docs wording, typo fixes, traducciones No PR solamente
Contenido del sitio web, entradas del blog No PR solamente

Escribiendo un RFC

Cómo escribir un buen RFC

Tres cosas que marcan la diferencia entre un RFC que se mueve rápido y uno que se para.

Establece el problema, no la solución

Comience con lo que se rompe o se pierde — no con lo que desea construir. Los evaluadores deben estar de acuerdo en que el problema es real antes de que puedan evaluar su solución propuesta. Enmarcar el "por qué" ante el "qué".

Mostrar cambios y alternativas

Un RFC fuerte explica qué más se consideró y por qué fue rechazado. Esto ahorra ciclos de revisión y da contexto a futuros usuarios cuando el autor original ha seguido adelante.

Sea específico sobre el impacto

¿Quién está afectado? ¿Qué depósitos, archivos o contratos públicos cambian? Cuanto más claro sea el alcance, más rápido puede la comunidad dar comentarios útiles y un encargado puede tomar una decisión.
