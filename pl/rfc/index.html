Co wymaga RFC?

Nie każda zmiana wymaga RFC — tylko istotne. Skorzystaj z poniższej tabeli, aby zdecydować.

Rodzaj zmiany Czy potrzebne RFC? Proces
Nowy filar lub usunięcie filaru Tak RFC → głosowanie TSC → PR
Zmiany modelu scoringu (poziomy PASS, wagi) Tak RFC → głosowanie TSC → PR
Zmiana łamiąca zgodność schematu kontroli lub ich ID Tak RFC → głosowanie TSC → PR
Propozycja nowej grupy roboczej Tak RFC → lazy consensus → opublikowanie statutu
Zmiany governance lub ról Tak RFC → kwalifikowana większość TSC
Nowa kontrola (zgodna wstecz, uzupełniająca) Zalecane PR z linkiem do dyskusji, lazy consensus
Sformułowania w dokumentacji, literówki, tłumaczenia Nie Tylko PR
Treści strony, wpisy na blogu Nie Tylko PR

Przebieg statusów RFC.

Każde RFC przechodzi tę samą udokumentowaną ścieżkę, od pierwszego szkicu do zamkniętej decyzji.

draft
Autor pisze propozycję w GitHub Discussions
→
open
Co najmniej 5 dni roboczych otwarte na komentarze społeczności
→
accepted
Głosowanie TSC lub lazy consensus, publicznie udokumentowane
→
implemented
PR zmergowany, wpis w dzienniku zmian dodany, RFC zamknięte
Inne możliwe wyniki: rejected (nieprzyjęte po przeglądzie), withdrawn (wycofane przez autora). Oba są dokumentowane wraz z uzasadnieniem.

Jak napisać dobre RFC.

Trzy rzeczy, które decydują o tym, czy RFC posuwa się szybko, czy utknie.

Opisz problem, nie rozwiązanie

Zacznij od tego, co nie działa lub czego brakuje, a nie od tego, co chcesz zbudować. Recenzenci muszą zgodzić się, że problem jest realny, zanim ocenią proponowane rozwiązanie. Wyjaśnij „dlaczego” przed „co”.

Pokaż kompromisy i alternatywy

Dobre RFC wyjaśnia, co jeszcze rozważano i dlaczego to odrzucono. Oszczędza to rund przeglądu i daje kontekst przyszłym maintainerom, gdy autora nie ma już w projekcie.

Precyzyjnie opisz wpływ

Kogo to dotyczy? Które repozytoria, pliki lub publiczne kontrakty się zmieniają? Im jaśniejszy zakres, tym szybciej społeczność da przydatną informację zwrotną, a maintainer podejmie decyzję.
