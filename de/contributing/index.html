Wege zum Mitwirken.

Code, Inhalte, Community — wählen Sie, was zu Ihren Fähigkeiten und Ihrer Zeit passt.

PRs & Issues

Bugs beheben, Controls umsetzen, Tooling verbessern. Jeder PR wird von einem Maintainer geprüft und mit einer Entscheidung verknüpft.

Doku & Patterns

Schreiben Sie Säulendokumentation, Referenzarchitekturen, Best-Practice-Patterns oder konkrete Beispiele aus echten Projekten.

RFC-Reviews

Kommentieren Sie offene RFCs, schlagen Sie Alternativen vor oder stimmen Sie über Framework-Entscheidungen ab. Jede Stimme zählt — besonders die Perspektive aus der Praxis.

Lokalisierung

Helfen Sie, Inhalte ins Deutsche, Englische oder in weitere Sprachen zu übersetzen. WAF++ soll für die globale Cloud-Community zugänglich sein.

Working Groups

Treten Sie einer Working Group zu einer bestimmten Säule, zum Scoring-Modell, zur Controls-Bibliothek oder zu einer Referenzarchitektur bei — oder schlagen Sie eine vor.

Talks & BoFs

Stellen Sie WAF++ auf einer Konferenz vor, veranstalten Sie eine Birds-of-a-Feather-Session oder leiten Sie einen Community-Workshop. Praxiserfahrung ist Gold wert.

Erste Schritte.

Vier Schritte vom Neuling zum Contributor.

  1. Die GitHub-Organisation erkunden

    Durchstöbern Sie offene Issues mit dem Label good first issue oder help wanted unter github.com/{{ site.data.github.org }}. Noch kein passendes Issue? Eröffnen Sie eines und beschreiben Sie, was Sie angehen möchten.

  2. Stellen Sie sich auf Slack vor

    Treten Sie der Community auf Slack bei, sagen Sie Hallo in #general, stellen Sie Fragen und finden Sie heraus, welche Working Group zu Ihrem Hintergrund und Ihren Interessen passt.

  3. Fork → Branch → PR

    Forken Sie das passende Repository, legen Sie einen Feature-Branch an und eröffnen Sie einen Pull Request. Ein Maintainer prüft ihn, gibt Feedback und begleitet Sie durch den Prozess.

  4. Größere Änderungen? Erst einen RFC eröffnen

    Für neue Säulen, Breaking Changes, Scoring-Änderungen oder Governance-Updates — entwerfen Sie einen RFC in GitHub Discussions. Die Community prüft ihn, bevor die Umsetzung beginnt. So bleiben Entscheidungen nachvollziehbar.

Working Groups.

Working Groups sind themenbezogene Teams, die bestimmte Teile von WAF++ entwickeln. Jede und jeder kann eine vorschlagen — nötig sind nur eine Charta, mindestens eine Leitung und ein Maintainer als Pate.

Eine WG finden

Sehen Sie sich offene WG-Vorschläge in GitHub Discussions an und treten Sie dem passenden Slack-Kanal bei. Sie können ohne Vollzeitverpflichtung mitwirken.

Eine WG gründen

Entwerfen Sie eine Charta in einer GitHub-Diskussion, finden Sie einen Maintainer als Paten und kündigen Sie die WG auf Slack an. WGs können jeden Zuschnitt haben: eine einzelne Säule, eine Tooling-Frage, einen Scoring-Ansatz.

Ergebnisse liefern

WG-Ergebnisse fließen als PRs und RFCs zurück. Jedes Ergebnis ist öffentlich, nachvollziehbar und zitierfähig — im Einklang mit den Transparenzprinzipien von WAF++.

Feature-Lebenszyklus.

Jede Fähigkeit von WAF++ durchläuft einen klaren Lebenszyklus. Jede Stufe ist an den RFC-/ADR-Prozess gebunden, sodass Nutzer jederzeit wissen, wie ausgereift ein Feature ist und was sie vor der Einführung erwartet.

Closed Alpha

Privat erkunden

Eine kleine Gruppe von Early Adopters testet die Fähigkeit in kontrollierten Umgebungen. API, Scoring-Modell oder CLI-Oberfläche sind bewusst instabil und können sich ohne Ankündigung ändern.

So gelangt ein Feature hierher
  • Ein RFC-Entwurf oder offener RFC definiert das Experiment
  • Early-Access-Kohorte nur auf Einladung
  • Feedback treibt schnelle Iterationen
RFC-Entwürfe ansehen →
Alpha

Öffentlich testen

Die Fähigkeit steht allen zur Verfügung, die sie ausprobieren möchten. Schnittstellen sind weitgehend stabil, Breaking Changes aufgrund von Community-Feedback sind aber noch möglich.

So gelangt ein Feature hierher
  • RFC mit Alpha-Umfang angenommen
  • Öffentliche Doku und Release Notes verfügbar
  • GitHub Discussions sammeln Feedback
An Alpha-Diskussionen teilnehmen →
Beta

In Produktion nutzen

Die Fähigkeit ist funktional vollständig und für die dokumentierten Anwendungsfälle produktionsreif. Kleinere Anpassungen sind noch möglich, Breaking Changes erfordern jedoch eine ausdrückliche Migrationsanleitung.

So gelangt ein Feature hierher
  • RFC angenommen und Umsetzung gemergt
  • Ein ADR dokumentiert die Kriterien für Produktionsreife
  • Sicherheits-, Performance- und Kompatibilitätsprüfung bestanden
Angenommene RFCs verfolgen →
GA

Allgemeine Verfügbarkeit

Die Fähigkeit wird vollständig unterstützt, fällt unter die Stabilitätsrichtlinie und wird allen Nutzern empfohlen. Sie wird mit abwärtskompatiblen Updates und klaren Deprecation-Fristen gepflegt.

So gelangt ein Feature hierher
  • Der RFC-Status wechselt zu implemented
  • Ein abschließender ADR bestätigt den stabilen Vertrag
  • Aufnahme in den offiziellen Release-Train
Umgesetzte RFCs ansehen →

Jede Stufe ist an den RFC-/ADR-Prozess gebunden. Wird ein RFC angenommen, löst er die Alpha- oder Beta-Stufe aus; wird er als implemented markiert, ist die Fähigkeit bereit für GA. Den Gesamtüberblick finden Sie im RFC-Tracker — oder schlagen Sie die nächste Änderung in GitHub Discussions vor.

Der RFC-Prozess.

Wesentliche Änderungen durchlaufen einen RFC (Request for Comments). Der Prozess ist schlank, stellt aber sicher, dass jede Entscheidung von der Community geprüft und dokumentiert wird.

Kein Beitrag ist zu klein.

Eine Tippfehlerkorrektur, ein klärender Kommentar, ein Review — alles bringt das Framework voran. WAF++ entsteht öffentlich, und die Community steht immer offen.
