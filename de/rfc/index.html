Was ist ein Fall für einen RFC?

Nicht jede Änderung braucht einen RFC, nur wesentliche. Die Tabelle unten hilft bei der Entscheidung.

Art der Änderung RFC nötig? Prozess
Neue Säule oder Entfernen einer Säule Ja RFC → TSC-Abstimmung → PR
Änderungen am Scoring-Modell (PASS-Stufen, Gewichtungen) Ja RFC → TSC-Abstimmung → PR
Breaking Change am Controls-Schema oder an IDs Ja RFC → TSC-Abstimmung → PR
Vorschlag für eine neue Working Group Ja RFC → Lazy Consensus → Charta veröffentlicht
Änderungen an Governance oder Rollen Ja RFC → qualifizierte TSC-Mehrheit
Neuer Control (nicht breaking, ergänzend) Empfohlen PR mit Link zur Diskussion, Lazy Consensus
Formulierungen in der Doku, Tippfehler, Übersetzungen Nein Nur PR
Website-Inhalte, Blogartikel Nein Nur PR

Status-Ablauf eines RFC.

Jeder RFC folgt demselben dokumentierten Weg, vom ersten Entwurf bis zur abgeschlossenen Entscheidung.

draft
Die autorisierende Person schreibt den Vorschlag in GitHub Discussions
→
open
Mindestens 5 Werktage offen für Kommentare der Community
→
accepted
TSC-Abstimmung oder Lazy Consensus, öffentlich dokumentiert
→
implemented
PR gemergt, Changelog-Eintrag ergänzt, RFC geschlossen
Alternative Ergebnisse: rejected (nach Prüfung nicht angenommen), withdrawn (von der autorisierenden Person zurückgezogen). Beides wird mit Begründung dokumentiert.

So schreiben Sie einen guten RFC.

Drei Dinge, die den Unterschied machen zwischen einem RFC, der schnell vorankommt, und einem, der ins Stocken gerät.

Beschreiben Sie das Problem, nicht die Lösung

Beginnen Sie mit dem, was kaputt ist oder fehlt, nicht mit dem, was Sie bauen wollen. Reviewer müssen sich einig sein, dass das Problem real ist, bevor sie Ihren Lösungsvorschlag bewerten können. Klären Sie das „Warum“ vor dem „Was“.

Zeigen Sie Abwägungen und Alternativen

Ein starker RFC erklärt, was sonst noch erwogen und warum es verworfen wurde. Das spart Review-Runden und gibt künftigen Maintainern Kontext, wenn die ursprüngliche autorisierende Person nicht mehr dabei ist.

Seien Sie konkret bei den Auswirkungen

Wer ist betroffen? Welche Repositories, Dateien oder öffentlichen Verträge ändern sich? Je klarer der Umfang, desto schneller kann die Community nützliches Feedback geben und ein Maintainer entscheiden.
